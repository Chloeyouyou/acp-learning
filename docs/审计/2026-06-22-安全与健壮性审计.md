## 🔴 高危

### #1 沙箱把父进程全部环境变量（含 API Key）灌进学生代码 → 密钥可被偷

- **定位**：`backend/app/services/sandbox.py:19`
- **现象**：`_UTF8_ENV = {**os.environ, ...}` 让 `subprocess` 子进程继承父进程**全部**环境变量。`config.py` 启动时 `load_dotenv()` 把 `DEEPSEEK_API_KEY` 注入 `os.environ`，于是任何提交到 `/api/sessions/{id}/run` 的代码都能读到它。`/run` 是无鉴权公开端点 → 任何人提交三行代码即可窃取 key。
- **证据**（实测）：
  ```
  提交：import os; print(os.environ.get("DEEPSEEK_API_KEY"))
  返回：sk-…（长度 35）   ← 泄露成立
  ```
- **修法**：给子进程传**最小白名单 env**，不要展开 `os.environ`：
  ```python
  # sandbox.py
  _UTF8_ENV = {
      "PYTHONUTF8": "1",
      "PYTHONIOENCODING": "utf-8",
      "PATH": os.environ.get("PATH", ""),
      "SYSTEMROOT": os.environ.get("SYSTEMROOT", ""),  # Windows 下 Python 启动需要
  }
  ```
  改完跑一遍 `run_tests.py` 的 `sandbox_基本`，并手测一段读环境变量的代码确认拿不到 key。

### #2 SPA 兜底路由存在路径穿越 → 任意文件读取

- **定位**：`backend/app/main.py:454-457`（`_spa` 路由）
- **现象**：`candidate = _DIST / full_path` 后直接 `FileResponse(candidate)`，**没有目录包含校验**。线上单服务部署（`frontend/dist` 存在时该路由激活）下，构造 `..%2f..%2fbackend/.env` 可读到密钥、`acp.db`、源码。
- **证据**（实测）：
  ```
  _DIST / "../../backend/.env"  →  is_file() = True，resolve() 落在 dist 之外
  ```
- **修法**：解析后校验仍在 dist 内：
  ```python
  @app.get("/{full_path:path}")
  def _spa(full_path: str):
      if full_path.startswith("api/") or full_path == "api":
          from fastapi.responses import JSONResponse
          return JSONResponse({"detail": "Not Found"}, status_code=404)
      candidate = (_DIST / full_path).resolve()
      if full_path and candidate.is_file() and candidate.is_relative_to(_DIST.resolve()):
          return FileResponse(candidate)
      return FileResponse(_DIST / "index.html")
  ```
  （`is_relative_to` 需 Python ≥ 3.9；本项目 3.12，OK。）

### #3 学生数据零鉴权 → 任意越权读取（IDOR）

- **定位**：`backend/app/main.py` 所有 `/api/students/{student_id}/*`（profile / timeline / capabilities / review-queue / active-sessions / recommendations）
- **现象**：直接采信 URL 里的 `student_id`，无任何身份校验。轻量身份用的是**真实学号**（`frontend/src/api.js:18`），公网部署时枚举学号即可读取任意同学的全部画像与会话历史。
- **定性**：这是「无密码轻量身份」方案的**已知取舍**，不是实现 bug。但部署到公网前必须明确：**全体学生数据 = 按学号可枚举公开**。
- **修法（按投入从低到高）**：
  1. 最低成本：把 `student_id` 从「裸学号」改成「学号 + 服务端盐做的不可枚举 token」，前端存 token、URL 不出现裸学号。
  2. 中等：加一层最简会话凭证（登录时签一个 HMAC cookie，端点校验 cookie 里的 id == 路径 id）。
  3. 见 `docs/design` 里的登录方案落地后统一收口。
- **关联**：`/api/admin/...`（`main.py:340`）靠 `ACP_ADMIN_TOKEN`，但**默认不设就全开**——忘配一次 = 所有学生完整对话史外泄。部署清单里务必把「设置 `ACP_ADMIN_TOKEN`」列为必做项；并把比较改成 `hmac.compare_digest(token or "", required)` 避免时序侧信道。

## 🟡 中（健壮性 / 部署）

### #4 LLM 调用没有任何超时

- **定位**：`backend/app/services/tutor.py:544`、`590`
- **现象**：`client.chat.completions.create(...)` 未传 `timeout=`，OpenAI SDK 默认 **600 秒**。DeepSeek 抖动时单请求占住线程池 worker 长达 10 分钟，几个并发即可拖垮同步端点。`run_turn` 虽有 try/except 兜底，但超时本身先把用户卡死。
- **修法**：在 client 上统一设超时（一处生效）：
  ```python
  # tutor.py
  client = OpenAI(
      api_key=os.getenv("DEEPSEEK_API_KEY"),
      base_url=DEEPSEEK_BASE_URL,
      timeout=30.0,        # 秒
      max_retries=1,
  )
  ```

### #5 依赖未锁版本

- **定位**：`backend/requirements.txt`（全是 `fastapi>=0.115` 这类下限约束）
- **现象**：pydantic / openai / fastapi 任一发布 breaking 版本，全新 VPS 部署会在无代码改动下崩。
- **修法**：在已知可用的 venv 里 `pip freeze > requirements.lock.txt`，部署用 lock 文件；或把关键库改成兼容性区间（如 `fastapi>=0.115,<0.120`）。

### #6 `@app.on_event("startup")` 已废弃

- **定位**：`backend/app/main.py:31`
- **现象**：新版 FastAPI 将移除 `on_event`，应迁移到 `lifespan`。不紧急，但早迁早省事。
- **修法**：
  ```python
  from contextlib import asynccontextmanager

  @asynccontextmanager
  async def lifespan(app: FastAPI):
      init_db()
      mine_engine.load_patterns()
      yield

  app = FastAPI(title="ACP Learning API", version="0.1.0", lifespan=lifespan)
  ```

### #10 ④修复缺规则门 → 不改代码也能被标「已内化」（整合性漏洞，已修）

- **定位**：`tutor.py:run_turn` 的 `allow_transition` 段——③→④ 有根因门、⑤→⑥ 有假设检验门，**唯独 ④修复 这道「真判题」硬门是空的**。
- **现象**：离开 ④修复 的唯一合法路径本应是「提交通过」（`main.py:submit_fix` 里 `judge_fix` 通过后直接置 `stage=⑤ + mine_status=fixed`，不走对话路径）。但 `run_turn` 里 ④→⑤ 的 LLM 跃迁没有任何门控，LLM 只要在对话中填 `stage_transition`，学生就能被推过这道门。
- **证据**（两段 repro 实测）：构造一个在 ④修复 时返回 `stage_transition=⑤验证` 的导师，配合后续 ⑤→⑥、⑥三轴达成，会话走到 `mine_status=internalized`、`status=completed`、知识点「已内化」——而**代码从头到尾没提交过、没跑过 `judge_fix`**。「修对≠学会」的整个保证被绕过。
- **修法（已实施）**：在 `allow_transition` 段补一道门：
  ```python
  # ④→⑤放行门控（真判题硬门）：还没 fixed 时，LLM 在对话中的任何跃迁一律拦下
  if allow_transition and stage_before_llm == "④修复" and session.mine_status != "fixed":
      allow_transition = False
  ```
  因为合法的 ④→⑤ 由 `submit_fix` 直接设阶段、不经此路径，加门不影响正常流。
- **回归测试**：`run_tests.py` 新增两条——`状态机_修复阶段未提交时LLM不得擅自跃迁`（门挡住）、`状态机_提交通过后可正常进验证`（fixed 后正常放行，不误伤）。共 47/0。
- **可选加固（未做）**：⑥内化结算块（`tutor.py` 内化判定）可加 `session.mine_status == "fixed"` 前置做纵深防御；根因已由 ④ 门堵死，故暂留最小改动。

## 🟠 前端审计（方向② · `frontend/src/views/Arena.vue`，2026-06-22）

### #14 ⑤验证「不能运行/不能改码」与导师流程直接冲突（🟠 学习闭环硬伤，**待决策**）

- **现象**：提交通过后 `session.fixed=true`。此时**运行按钮被禁用**（`Arena.vue:611` `:disabled="...|| session.fixed"`）、**代码框只读**（`Arena.vue:623` `:disabled="session.fixed"`），且 `runAndCheck` 在 `session.fixed` 时**直接 return**（`:515`）。即 ⑤验证、⑥内化 全程**既不能跑代码、也不能改代码**。
- **冲突**：后端 ⑤验证 导师剧本（`VERIFY_LAYER_TEMPLATE`）通篇要求「学生提边界输入 → **点运行亲自跑出来** → 真实结果自动进对话再对照」；最高红线 #7 又禁止导师在没有真实运行结果时断言输出。结果：**导师反复让学生「去点运行」，而按钮是灰的**；导师又不能替他断言——⑤验证 沦为纯嘴上谈，`Hypothesis_Testing`（动手验证假设）这一核心能力**在 UI 上根本无法练**。
- **更深一层**：即便放开禁用，`runAndCheck` 逻辑也不对——它「代码变了就走 `submit()`」，而 ⑤ 里 `originalCode` 未更新、`codeChanged` 恒真，于是点运行会触发 `submit()`，又被 `submit_fix` 的 `mine_status=="fixed"` 短路成「已通过无需重复」，**仍跑不了边界输入**。
- **后端其实支持**：`/run` 端点在 `status=="active"` 时照常接收并注入运行结果（`main.py:162`）；⑤ 时会话仍 active。**纯前端门把它焊死了。**
- **修法方向（需决策，非一行）**：⑤验证（`fixed && !done`）应允许跑代码 + 改输入；运行按钮在 `fixed` 时走**纯运行** `runCurrentCode`（不再 `submit`）；代码框只在 `session.done` 后才只读。属学习流程行为变更，建议确认后再改。

## 📊 算分 / 画像审计（`profile.py` + `event_engine.py` + `registry.py`，2026-06-22）

### #18 维度分只对「有证据的子能力」求平均 → 单个子能力能把整维度顶到 100（🟠 高估能力，**待决策**）

- **现象**：`get_profile`（`profile.py:54-63`）算「Debug能力 / AI协作能力」时，**只把有事件的子能力计入分母**（`cap in vector`）。Debug能力 名下有 5 个子能力（日志阅读/边界/根因/独立调试/假设验证，权重和=1.0），若学生只触发过其中 1 个，维度分 = 那 1 个的分。
- **实测**：连发 4 条 `Independent_Debug +3` → 该能力 100 分 → **Debug能力 维度显示 100.0、confidence「normal」**，而另外 4 个子能力 0 证据。学生看到「Debug 能力 100 分（证据充足）」，实际只练了 1/5。
- **置信度也失灵**：`confidence` 看的是该维度**总事件数** `n<5→low`；同一能力刷 5 次就翻成「normal」，并不要求覆盖多个子能力。
- **影响**：画像/数字孪生的核心卖点是「诚实的能力镜子」，这个高估直接动摇可信度。
- **修法方向（需决策）**：① 维度分对**全部已注册子能力**求平均（没证据的按基线如 `INITIAL_SCORE`/0 计入分母，让未练的拉低分）；或 ② 置信度改看「有证据的**不同子能力**数」而非总事件数（≥1 个能力独大时维持 low）。属画像口径变更，影响学生所见，确认后再改。

### #19 冷启动×2 几乎常驻 → 能力分约 4 次成功即封顶（🟡）
- `apply_event`：`INITIAL=30`，`events<10` 时系数 ×2，`BASE_STEP=3`。规则事件 conf=1.0 → 每条 `+3×3×2=+18`，**30→48→66→84→100，4 条封顶**；单条事件就摆动 18 分。由于很少有人在单个能力上攒到 10 条，冷启动×2 实际几乎一直生效，分值偏粗、早期波动大、很快触顶。属调参问题，记录备查。

### #20 Internalization 不进任何可见维度（🟢）
- `registry.py` 里 `Internalization` 的 `dimension="*"`、`weight=0`，于是 `on_internalized(+3)`/`on_transfer_confirmed(+2)` 的得分只进 `vector`、**不进 Debug/AI 两个维度**。学生内化再多，两个大维度数字也不动。可能是有意（内化由知识点状态体现），记录备查。

### #21 已补 4 条算分测试（55 → 59）
- `算分_冷启动加倍且封顶100`、`算分_负向事件下探不破0`（钳位）、`算分_低置信LLM事件入库但不进分`（置信门）、`掌握度_状态映射与薄弱判定`（已内化→掌握 / 已解决→在学+weak / 已接触→生疏+weak）。
- **未锁** #18 的维度行为（那是待修的可疑口径，不写进回归以免固化）。仍缺：`recommend_patterns` 贪心排序、`get_weakest_pattern_id` 综合评分、`transfer_source`/`pick_variant`。

> **算分小结**：钳位、置信门、知识点状态映射这些**底层是对的**（已加测试锁住）。真正要你拍板的是 #18——**维度分会把单一子能力的高分当成整维度的高分，且标成「证据充足」**，对一个主打「诚实画像」的产品是要害。建议优先决策修不修、按哪种口径修。
