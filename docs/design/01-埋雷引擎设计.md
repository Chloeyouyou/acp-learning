# 埋雷引擎设计 V0.2

> 职责：按教学目标，在练习/项目代码中有意植入 Bug，并产出供 AI 导师和能力事件引擎使用的「雷清单（Ground Truth）」。

---

## 1. 核心概念

```text
Bug模式库（BugPattern）   ← 教学资产，按知识点/能力维度编目
        ↓ 选雷策略（根据学生画像）
雷实例（PlantedMine）     ← 植入到具体代码中的一颗雷
        ↓
雷清单（MineManifest）    ← 本次练习全部雷的Ground Truth，学生不可见
                            供AI导师引导、供事件引擎判定
```

**关键设计**：每颗雷都带完整元数据（位置、根因、预期修复、引导阶梯、内化问题）。AI 导师不是"现场看代码猜哪里有错"，而是**拿着标准答案做引导**——这保证引导质量稳定、不会被学生套出错误答案。

## 2. Bug模式库（BugPattern）

### 2.1 数据模型

```yaml
BugPattern:
  id: BP-BOUNDARY-001
  name: 循环边界差一错误（off-by-one）
  category: boundary            # 见2.2分类体系
  languages: [java, python, c]
  knowledge_points: [数组, 循环]
  capability_dims:              # 关联画像维度（见能力事件模型）
    - Debug能力.边界意识
    - 编程能力.数组
  difficulty: L1                # L1-L5
  symptom: RE                   # 学生可观察的现象：CE/RE/WA/HANG/PERF/SILENT
  mutation_rule: "i < n → i <= n"   # 变换注入规则（可机器执行）
  root_cause_template: "循环条件包含了arr.length本身，访问越过数组末尾"
  fix_template: "将 <= 改为 <"
  hint_ladder_ref: HL-BOUNDARY-001  # 引导阶梯模板（AI导师策略文档）
  internalize_questions:        # 内化环节反向提问
    - "为什么 i <= arr.length 会越界？数组下标的范围是什么？"
    - "如果要遍历到最后一个元素，正确条件是什么？"
  variants:                     # 变式池：同模式换场景
    - "字符串charAt遍历越界"
    - "二维数组行列边界混淆"
```

### 2.2 分类体系（V0.2 首批 8 类）

| 分类 | 代号 | 典型模式 | 主要症状 |
|------|------|----------|----------|
| 边界类 | boundary | off-by-one、空集合访问、字符串越界 | RE/WA |
| 空值类 | null | 空指针、未初始化、可选值未检查 | RE |
| 循环类 | loop | 死循环、循环变量误更新、break/continue误用 | HANG/WA |
| 递归类 | recursion | 缺少基准条件、状态未收敛、栈溢出 | RE/HANG |
| 逻辑类 | logic | 条件取反、运算符优先级、浅拷贝误用 | WA/SILENT |
| SQL类 | sql | 注入风险、JOIN条件缺失、NULL比较 | WA/SILENT |
| API类 | api | 未处理错误响应、参数顺序错、异步未await | RE/SILENT |
| 资源类 | resource | 文件/连接未关闭、内存泄漏 | PERF/SILENT |

> `SILENT`（不报错但结果错/有隐患）类雷难度最高，用于训练「不盲信能跑的代码」——尤其用在 Vibe Coding 训练场审查 AI 生成代码的场景。

### 2.3 难度分级

| 级别 | 定义 | 示例 |
|------|------|------|
| L1 | 单点雷，报错信息直指位置 | 数组越界，栈直接给出行号 |
| L2 | 单点雷，报错位置 ≠ 根因位置 | 第80行空指针，根因是第30行没赋值 |
| L3 | 需要构造输入/写测试才能触发 | 仅当输入为空列表时WA |
| L4 | SILENT雷，需要代码审查发现 | 浅拷贝导致偶发数据污染 |
| L5 | 多雷耦合/跨模块 | API错误被吞掉，表现为下游SQL查不到数据 |

## 3. 注入方式

| 方式 | 说明 | 适用 |
|------|------|------|
| 模板题 | 人工预写的带雷代码，质量最高 | 冷启动、L1-L2，MVP首选 |
| 变换注入 | 对正确代码执行 mutation_rule（类似变异测试），机器可批量生成 | L1-L3，规模化 |
| AI生成注入 | LLM按指定BugPattern重写正确代码植雷，再用测试套件验证"雷确实会响、且只响这一颗" | L3-L5、Vibe Coding场景 |

**AI生成注入的质检流水线**（必须，防止AI埋出意外的雷）：

```text
正确代码 + 指定BugPattern
↓ LLM植雷
带雷代码
↓ 跑完整测试套件
校验1：预期触发的测试确实失败（雷会响）
校验2：其余测试全部通过（没有埋出多余的雷）
校验3：LLM复核生成的root_cause与PatternID一致
↓
入库，生成MineManifest
```

## 4. 选雷策略（个性化）

输入：学生能力画像。输出：本次练习植入哪些雷。

```text
规则1（补弱）：优先选学生画像中薄弱维度对应的BugPattern
规则2（间隔复现）：状态为「已解决未内化」的知识点，按间隔重复（1天/3天/7天）
            推送变式雷，通过则升级为「已内化」
规则3（最近发展区）：难度 = 学生该维度当前等级 +1，不越级
规则4（防套路）：同一模式连续出现不超过2次，穿插已掌握模式防止定式
```

## 5. 雷清单（MineManifest）—— 三大系统的数据契约

每次练习生成一份，**学生不可见**，是埋雷引擎 → AI导师 → 事件引擎之间的核心接口：

```json
{
  "manifest_id": "mm_20260612_0001",
  "exercise_id": "ex_array_101",
  "student_id": "stu_001",
  "mines": [
    {
      "mine_id": "mine_001",
      "pattern_id": "BP-BOUNDARY-001",
      "location": { "file": "Main.java", "line": 12 },
      "trigger_input": "[1,2,3]",
      "root_cause": "循环条件 i <= arr.length 导致访问 arr[3]",
      "expected_fix": "i < arr.length",
      "hint_ladder_ref": "HL-BOUNDARY-001",
      "internalize_questions": ["..."],
      "variant_pool": ["BP-BOUNDARY-001-v2", "BP-BOUNDARY-001-v3"],
      "status": "planted"   // planted → found → fixed → internalized
    }
  ]
}
```

`mines[].status` 的每次跃迁都会触发能力事件（见能力事件模型文档）。

## 6. MVP 范围

- Bug模式库：boundary / null / loop 三类，共 15 个模式（人工编写）
- 注入方式：仅模板题
- 选雷策略：仅规则2（间隔复现）+ 固定难度
- 变换注入、AI生成注入、规则1/3/4 留到 V0.3
