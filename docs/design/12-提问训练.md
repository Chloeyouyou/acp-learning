# 12 · 提问训练（把「帮我看看」练成可协作的问题）

## 本文件的作用
定义「提问训练」从**前端写死的演示**演化为**真功能**的设计与分阶段（P0→P1→P2）。**本轮只出设计，不写代码。**
归属：五大模块里「AI 协作能力」训练的第一块；与 [[09-AI协作调试空间]]（共脑调试）并列，两者都喂同一个现在空着的「AI 协作」能力维度。
能力事件依据见 [[04-能力事件模型]] §4.9 `Prompt_Design`。

---

## 它是什么 —— 现状 vs 目标

| | 现在（demo） | 目标（真功能） |
|---|---|---|
| 提问内容 | 前端写死的 3 段台词，点「补一个要素」切换 | 学生写**自己的真实提问** |
| 诊断 | 写死的分数 / 三要素状态 | 知返用 **LLM 实时诊断**三要素 + 0~100 提问分 + 反馈 |
| 反馈 | 静态文案 | 针对学生这一版提问的具体建议 + 「再改一版」迭代 |
| 画像 | 无（且曾空许诺"+2"，已删） | P1 起落 `Prompt_Design` 能力事件，**点亮 AI协作维度** |

> 现在的 demo（`QuestionTraining.vue`，路由 `/question`）是 P0 的视觉与交互骨架，真功能在其上把"写死数据"换成"后端实时诊断"。

---

## 核心目标（不要跑偏）
**训练学生把「帮我看看 / 代码报错了」改写成一个 AI 真能接住的问题——即包含三要素：**
- **现象**：报了什么、看到什么（错误类型 / 实际表现）
- **上下文**：哪段代码、哪个文件、哪一行
- **预期**：你本来想要什么结果

这是一项**可迁移的协作素养**，不是某道题的答案。衡量它的货币就是 [[04-能力事件模型]] 的 `Prompt_Design`。

---

## 与能力事件 / 画像的关系（最大价值）
学生画像里 **AI协作能力现在是「未评估」**——系统从没产出过 `AI_Review / AI_Verification / Prompt_Design` 任一事件。
**提问训练是最快、最结构化的喂料口**：它直接产 `Prompt_Design`（`llm_judge`，归 AI协作维度，权重 0.30），一旦接入，画像里那根灰轴就活了。
落事件的唯一入口已存在：`event_engine.emit(...)`，`Prompt_Design` 已在注册表与 LLM 白名单内。

## 分阶段

| 阶段 | 做什么 | 接画像？ | 前置 |
|---|---|---|---|
| **P0（MVP）** | 几个**预置场景** + 学生写真实提问 → 后端 LLM 诊断三要素(各有无) + 0~100分 + 具体反馈 + 「再改一版」迭代 | ❌ **不记分、不动画像** | 文档定稿 |
| **P1** | 调 `emit(Prompt_Design)`：三要素全→+2 / 2项→+1；"一贴帮我看看"→-1。**点亮 AI协作维度** + 防刷；**+ 提问短板总结 → 个性化反馈**（见 §P1 个性化） | ✅ | **用户验收过 LLM 三要素判定质量** |
| **P2** | 学生**自带真实问题**泛化；闯关对话里**旁路**给提问打分（[[04-能力事件模型]] §4.9 的另一触发点） | ✅ | P1 稳定 |

**纪律（与 B0 一致的"先记不算分"）**：LLM 判三要素若判不准会**污染画像**。所以 P0 只做诊断与反馈、**坚决不落能力事件**；等用户人工验收判定靠谱，P1 再接画像。

## P0 详细设计

### 场景（预置）
一小组「学生会真的遇到」的场景，每个给一句背景，让学生据此写提问。例如：
- 登录功能跑不通（demo 现用的这个）
- 列表页数据读不出来 / 一直空白
- 函数返回结果不对（算出来的数和预期对不上）

每个场景配一对**差/好对照**（保留 demo 已有的对照卡）。

### 诊断（后端 LLM）
- 新端点：`POST /question-training/diagnose`，入参 `{scenario_id, prompt}`。
- LLM 判定并返回：
  ```json
  {
    "phenomenon": true,        // 现象是否说清
    "context": false,          // 上下文是否说清
    "expectation": false,      // 预期是否说清
    "score": 52,               // 0~100 提问分
    "feedback": "现象说清了；再告诉 AI 错在哪个文件/第几行，它就能精准定位。",
    "confidence": 0.86
  }
  ```
- **复用防幻觉地基**（见 [[acp-zhifan-no-sandbox-bug]]）：这里不跑代码，但导师提示同样禁止臆断"运行结果/正确答案"；只评估**提问本身**的三要素完整度，不替学生回答技术问题。
- **三要素 → 分** 对齐 [[04-能力事件模型]] §4.9：3 项全→高分段、2 项→中、≤1→低。具体分值映射 P0 先给经验值，P1 与 delta 规则对齐。

### 反馈与迭代
- 诊断后高亮**缺哪个要素**、给一句**怎么补**的具体建议。
- 「再改一版」：学生改写后重新诊断，看分数/三要素变化（进步可视）。

### 前端
在现有 `QuestionTraining.vue` 上改：
- 选场景 → **真实输入框**（替换写死台词）→ 提交 → 知返实时诊断（替换写死数据）→ 「再改一版」。
- 保留：差/好对照卡、提问分进度条、三要素 ○/✓、知返点评区。

### P0 明确不做
- 不落任何能力事件、不动画像、不算分。
- 不让 AI 替学生写技术答案（这是**提问**训练，不是问答）。
- 不接闯关对话旁路（留 P2）。
- **不持久化**：提问历史只活在前端本次会话内（刷新即没）。"总结短板/个性化"需要跨会话数据，属 P1。

## P1 · 提问短板总结 → 个性化反馈

> 复用闯关里已验证的同款机制：成长轨迹的「**你常见的思维默认值**」（`timeline.py` 跨题聚合反复犯的同类错）+ 开题时的个性化提醒（`intervention_for`）。提问训练做一个平行版：跨多次提问统计「**你最常漏哪个要素**」，让知返的反馈/提示**针对你的弱项**说话。

### 数据从哪来（依赖 P1 的持久化）
- P1 既然要 `emit(Prompt_Design)`，就**顺带把每次诊断的三要素结果存进证据**：`evidence.summary` 写"缺了预期"之类，`evidence.refs` 含 `{missing: ["expectation"], scenario_id, prompt}`。
- 这样无需新表——**直接从 `Prompt_Design` 的事件流回放**就能统计"最近 N 次里每个要素的缺失频次"。事件流本就是 append-only 的事实源（[[04-能力事件模型]] §5.1）。

### 怎么总结（轻量聚合，不引入新判定）
- 取该学生最近 N 次提问事件，数三要素各自被判 false 的次数。
- 选出**最常漏的 1 个要素**（如"预期：6/8 次没写"）作为"短板"；够样本量才给（如 ≥3 次提问），否则不显示——避免一两次就贴标签（对齐思维默认值的 `enough` 门槛）。

### 怎么个性化（喂给知返 + 前端提示）
- **文案纪律：不贴死标签。** 一律用"最近几次里，xxx 相对少一些"这类**观察式、非评判**措辞，**禁止**"你总是漏 xxx""你不会写 xxx"这类定性。对齐成长轨迹「镜子非审判」的口吻。
- **诊断反馈**：在 `diagnose` 的 system 提示里带上该学生的短板**作为软提示**（如"该学生最近几次里【预期】相对少一些，可在反馈里轻轻提醒"），让 feedback 更有的放矢，但仍只评本次提问。
- **输入框占位/开场**：进提问训练时若有短板，给一句观察式提醒（"最近几次你的【预期】写得相对少，这次可以先想想想要什么结果"）——平行于 `intervention_for`。
- **成长轨迹**：可选——把"提问短板"作为一条，融进现有「思维默认值」区或单列，同样用观察式措辞。

### P1 个性化的边界（务必保留）
1. **不贴死标签**：文案用"最近几次里，xxx 相对少一些"，不写"你总是漏 xxx"。
2. **样本量不足不展示**：达不到门槛（如 <3 次提问）就**完全不显示**短板总结/提醒。
3. **只影响措辞，不改加分**：短板仅用于提醒与反馈语气，**绝不改变** `Prompt_Design` 的加/扣分规则（加扣分仍只走 [[04-能力事件模型]] §4.9 的 delta）。
4. **统计来源只用事件流里的提问训练证据**：仅回放本学生的 `Prompt_Design` 事件（且 `confidence≥0.7`），**不引入任何外部数据**、不读闯关/其他模块。

## 防刷 + 防污染画像

| 关注 | P0 | P1 |
|---|---|---|
| 污染画像 | **完全不记分**（诊断纯展示） | 仅在用户验收判定质量后开启 |
| 刷分 | 不涉及 | **日上限**：`Prompt_Design` 每日正向 delta 合计封顶（对齐 [[04-能力事件模型]] §5.5 的 +6）；**会话上限**：单次训练会话最多记 N 次正向事件（防同一会话反复提交刷分） |
| 低质判定 | — | `confidence < 0.7` 的事件入库但不参与画像（沿用 `event_engine` 现有规则） |
| 证据 | — | `evidence.summary` = 三要素拆解结论，`refs` 含学生提问原文，供回放/复核 |

> P1 需要一个 `session_id` 才能 `emit`——给提问训练分配一种**轻量训练会话**（可新建简单会话记录，或用合成 id），细节 P1 设计时定。

---

## 拍板的决策（已确认）
1. **接画像时机**：P0 先不记分；**P1 再接 `emit(Prompt_Design)`，且前置 = 用户验收过 LLM 三要素判定质量**。
2. **定位**：独立训练模块，不在闯关里强插；闯关对话旁路打分留 P2。
3. **角色**：知返只**诊断提问**、不替学生答技术问题。
