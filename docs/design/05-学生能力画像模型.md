# 学生能力画像模型 V0.2

> 职责：把 04 文档产出的能力事件流，聚合成可解释、可回放、可驱动教学决策的学生画像。画像不是"积分榜"，而是「学生数字孪生」的第一个版本。

---

## 1. 设计原则

1. **画像是派生视图**：事件流是唯一事实源，画像可随时从头重放重算。改算法不改历史。
2. **每个数字可下钻**：画像 → 维度 → 能力向量 → 事件 → evidence 原文，四级钻取链路完整。说不清来源的分数不展示。
3. **状态与分值分离**：分值（0-100）回答"多强"，知识点状态机回答"到没到"。两者并行，互不替代。
4. **画像驱动教学**：画像不只是给人看的报表，它是选雷策略（01 §4）和导师策略（02 §4 画像摘要注入）的机器输入。

---

## 2. 画像数据结构

### 2.1 三层存储

```text
events                  # append-only 事件表（04定义），唯一事实源
capability_vectors      # 派生：能力向量快照表
knowledge_states        # 派生：知识点状态机表
```

### 2.2 能力向量表

```json
{
  "student_id": "stu_001",
  "as_of_event": "evt_20260612_000123",
  "updated_at": "2026-06-12T14:30:00+08:00",
  "vector": {
    "Log_Reading":          { "score": 44, "events_count": 12, "last_event_at": "..." },
    "Boundary_Awareness":   { "score": 38, "events_count": 21, "last_event_at": "..." },
    "Root_Cause_Reasoning": { "score": 52, "events_count": 9,  "last_event_at": "..." },
    "Independent_Debug":    { "score": 45, "events_count": 15, "last_event_at": "..." },
    "Hypothesis_Testing":   { "score": 41, "events_count": 7,  "last_event_at": "..." },
    "AI_Review":            { "score": 33, "events_count": 4,  "last_event_at": "..." },
    "AI_Verification":      { "score": 61, "events_count": 11, "last_event_at": "..." },
    "Prompt_Design":        { "score": 70, "events_count": 18, "last_event_at": "..." }
  }
}
```

`events_count` 同时是**置信度指标**：事件数 < 5 的能力分值在前端标记为「数据不足」，雷达图上用虚线渲染——3 个事件刷出来的 70 分和 30 个事件沉淀的 70 分不是一回事。

### 2.3 知识点状态表

```json
{
  "student_id": "stu_001",
  "knowledge_point": "数组",
  "state": "已解决",
  "related_patterns": {
    "BP-BOUNDARY-001": { "state": "已解决", "fixed_at": "...", "review_due": "2026-06-13" },
    "BP-BOUNDARY-004": { "state": "已内化", "internalized_at": "..." }
  },
  "review_queue": [
    { "variant_id": "BP-BOUNDARY-001-v2", "due": "2026-06-13", "interval_level": 1 }
  ]
}
```

知识点状态 = 其下所有相关模式状态的**最小值**（有一个模式只是"已解决"，知识点就不算"已内化"）。

## 3. 分值更新算法（V0.2）

选最简单可解释的版本，所有参数集中一处便于调参：

```text
score_new = clamp(score_old + delta × K, 0, 100)

K = BASE_STEP × confidence × repeat_factor × cold_start_factor

BASE_STEP         = 3
confidence        = rule事件恒1.0；llm_judge取事件值（<0.7已在入库时过滤）
repeat_factor     = 同一pattern_id第n次正向事件取 0.5^(n-1)，负向事件恒1.0
cold_start_factor = 该能力前10个事件取2.0，之后1.0
```

**时间衰减**（周任务批量执行）：

```text
某能力连续14天无事件 → 每周 score -1，衰减下限30
衰减事件本身也写入事件流（capability=X, delta=-1, producer=rule, evidence.type=decay）
——保证"画像可由事件流完整重放"的原则不被衰减破坏
```

**初始值 30 的含义**：30 代表"未知"，不代表"很差"。前端对 events_count=0 的能力显示「未评估」而非 30 分。

## 4. 四维画像聚合

```text
Debug能力   = Σ wᵢ × scoreᵢ ，i ∈ {Log_Reading 0.15, Boundary_Awareness 0.2,
              Root_Cause_Reasoning 0.3, Independent_Debug 0.25, Hypothesis_Testing 0.1}
AI协作能力  = AI_Review 0.35 + AI_Verification 0.35 + Prompt_Design 0.3
编程能力    = 知识点掌握度汇总：Σ(知识点状态权重) / 知识点总数 × 100
              （未接触0 / 已接触0.3 / 已解决0.6 / 已内化1.0）
系统设计能力 = V0.3 启用（等 Domain_Modeling 等事件类型注册）
```

权重设计依据：`Root_Cause_Reasoning` 权重最高（0.3）——它是"已解决"与"已内化"的分水岭能力；`AI_Review` 与 `AI_Verification` 等权——"会审查代码"和"会验证回答"是 AI 协作的两条腿。

权重是启动值，V0.3 后用真实数据校准（如用"变式独立通过率"作为外部效标做回归）。

## 5. 画像 API 形态（前端消费契约）

### 5.1 雷达图

```json
GET /api/students/{id}/profile

{
  "dimensions": [
    { "name": "Debug能力",   "score": 46, "trend_7d": +4, "confidence": "normal" },
    { "name": "AI协作能力",  "score": 55, "trend_7d": -2, "confidence": "normal" },
    { "name": "编程能力",    "score": 38, "trend_7d": +6, "confidence": "low" },
    { "name": "系统设计能力", "score": null, "status": "未启用" }
  ],
  "highlights": [
    "Root_Cause_Reasoning 连续3次独立归因成功",
    "BP-BOUNDARY-001 明天到期复现，通过即升级为已内化"
  ],
  "weaknesses": [
    "Boundary_Awareness 38分：近7天2次同模式触雷",
    "Independent_Debug：本周3次索要答案被拒"
  ]
}
```

### 5.2 下钻链路

```text
GET /profile                          # 四维雷达
GET /profile/dimensions/debug        # 维度 → 能力向量明细
GET /profile/capabilities/Boundary_Awareness/events   # 能力 → 事件流
GET /events/{event_id}               # 事件 → evidence（对话原文/diff/测试记录）
```

### 5.3 成长时间线

事件流的另一个视图：按周聚合，展示"本周内化了哪些知识点、哪些能力升降、为什么"。每条都引用具体事件——**成长报告里没有一句没有出处的话**。

## 6. 三种消费者视图

| 视图 | 看什么 | 特殊处理 |
|------|--------|----------|
| 学生 | 雷达图、成长时间线、待复现队列 | 负向事件展示为"待加强提醒"而非扣分通知；不展示与他人对比 |
| 教师 | 班级能力分布、共性薄弱模式（如"全班60%在BP-NULL-004卡住"）、个体钻取 | 共性薄弱模式直接反哺教学：该讲哪个知识点了 |
| 系统 | 选雷策略读 knowledge_states + vector；导师AI读画像摘要 | 机器接口，全量字段 |

---

## 7. 防作弊与数据质量

1. 继承 04 §5.5 全部防刷分机制（日上限、重复衰减、负向不封顶）
2. **异常模式检测**：分值短期暴涨（7天 +20 以上）自动标记，抽样复核其事件 evidence
3. **LLM判定审计**：每周抽样 5% 的 llm_judge 事件人工复核，判定准确率 < 85% 时收紧该类事件的 confidence 阈值
4. 画像永远展示 `as_of_event`——它声明了自己基于哪个事件点，可复现

## 8. 通往学生数字孪生

本画像是数字孪生路线的第一层。后续每层都建立在事件流之上，不需要重建数据：

```text
V0.2  能力向量 + 知识点状态机（本文档）
V0.3  错误模式本体：pattern间建立"易混淆/前置依赖"关系，画像能预测"他下一个会犯什么错"
V0.4  能力本体：能力间依赖图（先有Log_Reading才谈得上Root_Cause_Reasoning），定位成长瓶颈
V1.0  学生数字孪生：用画像模拟"给他这道题，他大概率卡在哪"，反向驱动出题
```

## 9. MVP 范围

- 三层存储 + §3 更新算法（不含时间衰减）
- 四维只做 Debug能力 与 AI协作能力；编程能力随知识点状态机一起上，系统设计能力留 V0.3
- API：雷达图 + 能力向量下钻 + 事件 evidence 查看（成长时间线留 V0.3）
- 视图：只做学生视图；教师班级视图留 V0.3
