# 能力事件模型 V0.2

> 职责：定义系统中唯一的「学习度量货币」。学生的一切学习行为最终都被翻译为强类型能力事件，沿「学生 → 能力事件 → 能力向量 → 画像」管道汇总。这是回答"学生到底有没有学会"的数据底座。

---

## 1. 能力事件是什么——以及为什么不是普通日志

### 1.1 定义

能力事件（Capability Event）是**一次有证据支撑的、关于学生某项能力的状态观测**。

它与普通行为日志的本质区别：

| | 行为日志 | 能力事件 |
|---|---------|---------|
| 记录的是 | 发生了什么操作 | 这次操作**证明了什么能力** |
| 主语 | 系统/页面 | 学生的某项能力 |
| 示例 | `student_001 提交了代码` | `Boundary_Awareness +2`（学生在L1提示下定位了边界错误） |
| 能否回放成画像 | 不能，需要二次解释 | 能，事件流本身就是画像的全部来源 |
| 必须携带 | 时间戳 | **能力类型 + 方向 + 证据** |

判别标准：一条记录如果删掉之后画像不受影响，它就不是能力事件，是日志。`发现Bug +2` 不是能力事件——"发现Bug"是行为；`Boundary_Awareness +2` 才是——它断言了一项**能力**的证据。

### 1.2 三条硬约束

1. **强类型**：`capability` 字段必须是本文档注册表中的类型，禁止自由字符串。新能力类型必须先注册（含触发条件、delta规则、evidence要求）才能产出。
2. **有证据**：每个事件必须携带 evidence——指向触发它的原始材料（对话原文、代码diff、测试结果）。无证据的事件在入库时被拒绝。
3. **可负向**：能力是观测出来的，不是攒积分。负向事件（依赖答案、重复犯错）与正向事件同等重要——没有负向事件的画像只会单调上涨，不可信。

## 2. 两类事件生产者

事件由两条独立管线产出，在事件总线汇合后统一入库：

```text
后端规则引擎（确定性事件）──┐
                            ├──→ 事件总线 → 校验（类型注册/evidence非空）→ 事件存储 → 画像聚合
导师AI（LLM判定事件）───────┘
```

### 2.1 后端确定性事件（rule）

由可机器判定的状态变化触发，**不经过 LLM，confidence 恒为 1.0**：

- MineManifest 中雷状态跃迁：`planted → found → fixed → internalized`
- 测试结果：触发测试由失败转通过、回归测试是否全绿
- 引导阶梯升级：每次 hint_level 上升
- 间隔复现结果：变式雷在 ≤L1 提示下是否独立通过
- 行为计数：同一 pattern 连续第 N 次犯错、连续 N 次索要答案

### 2.2 LLM判定事件（llm_judge）

由导师 AI 在对话中对**语义层面**的能力表现做判定，必须携带 confidence 与 evidence 原文：

- 学生是否主动提出假设、是否主动验证 AI 的回答
- 归因表述是否与 root_cause 语义一致
- Prompt 质量评估（上下文完整度、问题描述、拆解粒度）

**可信度规则**：`confidence < 0.7` 的事件入库但不参与画像计算（保留供人工复核与模型调优）；同一轮对话同一能力类型最多产出 1 个 LLM 判定事件。

**分工原则**：凡是规则引擎能判定的，绝不交给 LLM。LLM 只判定规则无法触及的语义层。

## 3. 事件统一 JSON Schema

```json
{
  "event_id": "evt_20260612_000123",
  "schema_version": "0.2",
  "student_id": "stu_001",
  "session_id": "sess_456",
  "timestamp": "2026-06-12T14:30:00+08:00",

  "capability": "Boundary_Awareness",
  "delta": 2,
  "polarity": "positive",

  "producer": "rule",
  "confidence": 1.0,

  "evidence": {
    "type": "mine_transition",
    "summary": "在L1提示下定位off-by-one雷，3轮对话内完成",
    "refs": {
      "mine_id": "mine_001",
      "pattern_id": "BP-BOUNDARY-001",
      "dialogue_turns": [3, 4, 5],
      "code_diff": "diff_789"
    }
  },

  "context": {
    "source_module": "bug_arena",
    "stage": "②定位",
    "hint_level": "L1",
    "knowledge_points": ["数组", "循环"],
    "exercise_id": "ex_array_101"
  }
}
```

字段约束：

| 字段 | 约束 |
|------|------|
| capability | 必须是第4节注册表中的类型 |
| delta | 整数，范围 [-3, +3]，具体取值由该能力类型的delta规则决定 |
| polarity | positive / negative，与delta符号一致（冗余字段，便于查询） |
| producer | rule / llm_judge |
| confidence | rule恒为1.0；llm_judge为[0,1]，<0.7不参与画像 |
| evidence | 必填。refs至少指向一个可回放的原始材料 |
| context.knowledge_points | 用于画像中"编程能力"维度按知识点细分聚合 |

## 4. 首批能力类型注册表（9类）

> 注册表是封闭集合。每类规定：触发条件、正向事件、负向事件、delta规则、evidence要求。

### 4.1 Log_Reading（日志/报错阅读）

| 项 | 内容 |
|----|------|
| 触发条件 | ①发现阶段，学生与报错信息/日志的交互 |
| 正向事件 | 学生从异常栈中自行读出错误类型、行号或关键参数（+1）；据此直接给出正确怀疑方向（+2） |
| 负向事件 | 看到报错不读，直接整段粘贴问"怎么办"（-1，单会话最多记1次） |
| delta规则 | 无提示读出 +2；L1提示后读出 +1；拒读 -1 |
| evidence要求 | llm_judge：引用学生复述报错内容的对话原文 |

### 4.2 Boundary_Awareness（边界意识）

| 项 | 内容 |
|----|------|
| 触发条件 | boundary类雷的定位/修复/复现，或学生在任意场景主动检查边界 |
| 正向事件 | 在≤L1提示下定位boundary雷（+2）；修复时主动补充空输入/极值测试（+2）；非雷场景代码中主动写对边界检查（+1） |
| 负向事件 | 同一boundary模式7天内重复触雷（-2）；修复一个边界却引入新的差一错误（-2） |
| delta规则 | 定位成功的delta按提示级别衰减：L0/L1→+2，L2/L3→+1，L4/L5→0 |
| evidence要求 | rule：mine_id + 提示级别记录；llm_judge：学生提出边界检查的对话原文 |

### 4.3 Root_Cause_Reasoning（根因分析）

| 项 | 内容 |
|----|------|
| 触发条件 | ③归因阶段，学生解释"为什么错" |
| 正向事件 | 归因表述与root_cause语义一致且自行说出（+3）；在L3原理提示后说出（+1） |
| 负向事件 | 改对了代码但归因仍错误/说不出（-1，且阻止阶段跃迁）；把症状当原因（"因为它报错了"）（-1） |
| delta规则 | 一致性由LLM比对root_cause_template判定；首次一致才计正分，同一雷重复表述不重复计分 |
| evidence要求 | llm_judge必填：学生归因原文 + 与root_cause的比对结论，confidence≥0.8才计分 |

### 4.4 Independent_Debug（独立调试）

| 项 | 内容 |
|----|------|
| 触发条件 | 一颗雷从found到fixed的全过程结束时结算 |
| 正向事件 | 全程≤L1提示完成修复（+3）；≤L2（+2）；≤L3（+1） |
| 负向事件 | 索要答案被拒后再次索要（-1/次）；连续3颗雷都依赖L4以上提示（-2）；连续三次依赖AI给答案（-1） |
| delta规则 | 每颗雷结算一次，取整个过程中用到的最高提示级别定档 |
| evidence要求 | rule：该雷全程hint_level序列 |

### 4.5 Hypothesis_Testing（假设验证）

| 项 | 内容 |
|----|------|
| 触发条件 | 学生提出可检验的猜测，或构造输入/测试去验证 |
| 正向事件 | 主动提出具体假设（"是不是空数组会挂"）（+1）；并自己动手构造输入验证（+2）；⑤验证阶段主动补回归测试（+2） |
| 负向事件 | 盲改代码碰运气（连续2次无理由修改后提交）（-1） |
| delta规则 | "提出"与"动手验证"分别计分，但同一假设链合计不超过+3 |
| evidence要求 | llm_judge：假设原文；rule：学生构造的输入/测试记录 |

### 4.6 Internalization（内化）

| 项 | 内容 |
|----|------|
| 触发条件 | ⑥内化环节三关（反向提问/复述/变式）的结算，及间隔复现结果 |
| 正向事件 | 三关全过（+3，该知识点状态跃迁为已内化）；间隔复现变式在≤L1下通过（+2） |
| 负向事件 | 已内化知识点再次触发同模式雷（-3，状态回退为已解决）；复述关失败（-1） |
| delta规则 | 只能由rule产出（三关结果是确定性的）；这是唯一能驱动「已解决→已内化」状态跃迁的事件类型 |
| evidence要求 | rule：三关各自的评分记录 + variant雷的提示级别 |

### 4.7 AI_Review（AI代码审查）

| 项 | 内容 |
|----|------|
| 触发条件 | Vibe Coding场景中学生对协作AI产出代码的审查行为 |
| 正向事件 | 主动发现协作AI代码中的教学性雷（+3）；提出有效质疑（"这里没处理空响应吧？"）（+2）；要求AI解释设计选择（+1） |
| 负向事件 | 未审查直接采纳含雷代码并提交（-2）；审查后仍漏掉SILENT级雷（-1） |
| delta规则 | "发现雷"按是否有导师提示定档（同4.2衰减规则）；"直接采纳"负分单次结算，不因多颗雷叠加 |
| evidence要求 | rule：雷状态+采纳行为记录；llm_judge：质疑/追问的对话原文 |

### 4.8 AI_Verification（AI回答验证）

| 项 | 内容 |
|----|------|
| 触发条件 | 学生对任意AI输出（解释、建议、代码）的验证行为 |
| 正向事件 | 主动验证AI回答（运行、查文档、写测试对照）（+3）；发现AI回答中的错误并指出（+3） |
| 负向事件 | 对AI的错误说法表示同意并据此行动（-2）；从不验证、全盘接受（按周结算，-1/周） |
| delta规则 | "验证"必须有动作证据（运行记录/引用文档），口头说"我觉得对"不计分 |
| evidence要求 | llm_judge：验证动作的对话原文 + 验证手段；rule：验证性运行/测试记录 |

### 4.9 Prompt_Design（提示词设计）

| 项 | 内容 |
|----|------|
| 触发条件 | 学生向协作AI提问时，导师AI旁路评估；及模块4专项训练 |
| 正向事件 | 提问包含「现象+上下文+预期」三要素（+2）；将大需求拆解为可执行的小步骤逐个提问（+2）；根据AI回答迭代改写提问（+1） |
| 负向事件 | 整段代码一贴+"帮我看看"（-1，单会话最多记2次） |
| delta规则 | 三要素按完整度评分：3项全有+2，2项+1，≤1项0分；专项训练场景按A/B对比评分 |
| evidence要求 | llm_judge：学生提问原文 + 三要素拆解结论 |

### 4.10 注册表汇总

| capability | 中文 | 主要producer | 归属画像维度 |
|------------|------|--------------|--------------|
| Log_Reading | 日志阅读 | llm_judge | Debug能力 |
| Boundary_Awareness | 边界意识 | rule | Debug能力 / 编程能力(按知识点) |
| Root_Cause_Reasoning | 根因分析 | llm_judge | Debug能力 |
| Independent_Debug | 独立调试 | rule | Debug能力 |
| Hypothesis_Testing | 假设验证 | 混合 | Debug能力 |
| Internalization | 内化 | rule | 全维度(按知识点归属) |
| AI_Review | AI代码审查 | 混合 | AI协作能力 |
| AI_Verification | AI回答验证 | 混合 | AI协作能力 |
| Prompt_Design | 提示词设计 | llm_judge | AI协作能力 |

> 系统设计能力维度的事件类型（Domain_Modeling / Interface_Design 等）随Vibe Coding训练场在V0.3注册。

## 5. 事件如何汇总成能力画像

### 5.1 管道

```text
事件流（append-only，永不修改）
↓ 过滤：confidence ≥ 0.7
↓ 聚合层1：能力向量（capability → score 0-100）
↓ 聚合层2：四维画像（向量按归属维度加权汇总）
↓ 并行：知识点状态机（未接触→已接触→已解决→已内化）
```

**事件流是唯一事实源**：能力向量和画像都是事件流的派生视图，可随时从头重放重算。调整算法不需要改历史数据。

### 5.2 聚合层1：能力向量

每个学生维护一个向量，每项能力一个 0-100 的分值：

```json
{
  "student_id": "stu_001",
  "vector": {
    "Boundary_Awareness": 38,
    "Root_Cause_Reasoning": 52,
    "Independent_Debug": 45,
    "AI_Verification": 61,
    "Prompt_Design": 70
  },
  "as_of_event": "evt_20260612_000123"
}
```

更新规则（V0.2 取简单可解释的版本）：

```text
score_new = clamp(score_old + delta × K, 0, 100)
K = 基础步长(3) × confidence
时间衰减：某能力连续14天无任何事件，每周 -1（最低衰减到30，防止"半年不练满级"）
冷启动：所有能力初始 30（"未知"而非"零"），前10个事件 K 翻倍以快速收敛
```

### 5.3 聚合层2：四维画像

```text
编程能力     = 按 context.knowledge_points 细分的知识点掌握度汇总
Debug能力    = Log_Reading + Boundary_Awareness + Root_Cause_Reasoning
              + Independent_Debug + Hypothesis_Testing 加权平均
AI协作能力   = AI_Review + AI_Verification + Prompt_Design 加权平均
系统设计能力 = V0.3 随对应事件类型注册后启用
```

四维分值用于雷达图展示；展开任一维可见其下能力向量明细，再展开可见每个分值背后的事件流与 evidence——**画像的每个数字都能点开看到证据**。

### 5.4 知识点状态机（与分值并行）

分值回答"多强"，状态回答"到没到"。每个知识点独立维护：

```text
未接触 → 已接触（首次相关事件）
       → 已解决（相关雷 fixed，由 Independent_Debug 结算事件驱动）
       → 已内化（Internalization +3 事件驱动，唯一入口）
回退：已内化状态下同模式触雷（Internalization -3）→ 降回已解决，重新进入间隔复现队列
```

选雷策略（01文档第4节）读取的就是这个状态机 + 能力向量——至此「埋雷 → 导师 → 事件 → 画像 → 选雷」闭环成环。

### 5.5 防刷分机制

1. **日上限**：同一能力类型每日正向delta合计封顶 +6
2. **重复衰减**：同一 pattern_id 的重复正向事件按 ×0.5 递减
3. **负向不封顶**：负向事件不设日上限
4. **evidence审计**：低confidence事件留档，定期抽样人工复核LLM判定质量

## 6. MVP 范围

- Schema 全量实现（append-only 事件表 + 派生向量表）
- 确定性事件：雷状态跃迁、提示级别、测试结果三类
- LLM判定事件：Root_Cause_Reasoning / Hypothesis_Testing / AI_Verification / Prompt_Design 四类
- 聚合：能力向量 + 知识点状态机；四维画像只做 Debug能力 与 AI协作能力 两维
- 时间衰减、防刷分的重复衰减留 V0.3
